# 0015. Tool Gateway, scopes and approvals; runs as resumable tool loops

- Status: Accepted. Amended 2026-10-30: approvals a call asks for by saying why (`whyAsks`). Addenda 2026-10-31: the step limit ends with Continuar; the cap becomes a backstop and runs that go in circles stop; approved ahead (`schedule_action`)
- Date: 2026-10-14
- Extends 0008.

## Decision

**Tools.** A `ToolDefinition` (name, description, JSON Schema input, `scope`, optional `connectionId`, `sensitive`, `describe`, `execute`) comes from a `ToolSource` (built-in tools, MCP connectors, sandbox). Sources never decide permissions.

**Scopes.** `agent_scopes (agent_id, connection_id, scope)` holds what an agent may do; `connection_id` null is a built-in scope (`context:read`, `memory:write`, `drive:*`, `issues:write`, `sandbox:run`). Grants are validated against the built-in list or the connector catalogs; nothing else can be granted.

**Tool Gateway** (`createToolGateway`), the only path from a model's tool call to execution:
1. look the tool up by name among the run's sources (the model's description of it is irrelevant);
2. check the scope in `agent_scopes` (database read on every call; no prompt can change it);
3. validate the input against the tool's JSON Schema (inputs stream eagerly, so the provider doesn't validate);
4. sensitive tools (flagged by the source, or any tool whose name or scope says merge, deploy or rollback) create an `approvals` row and stop; others run, with exceptions turned into error results;
5. record `tool_call`, `tool_result` and `approval` steps.

*Amended 2026-10-30:* a tool may also ask per call. A `whyAsks` tool (the computer's `run_code`, `run_skill_script` and `start_task`) creates the approval when the call carries a `why`: that is how an agent asks for a command the computer's policy held for a person (ADR 0053 §3, amended 2026-10-30). `executeApproved` runs the stored call with `approved` in its context, never from the input, and these tools pass it to the computer, which then runs that exact command.

**Approvals.** A row stores the tool, scope, connection, params and `action_hash = sha256(canonical JSON of all four)`, a title/detail for people, `expires_at` (24 h), and the agent's owner (snapshot). The agent's owner and org admins may decide (`decideApproval`), except a `request_permission` approval, which turns a connector or a built-in scope on for good: only admins (`manage_agents`) decide it (`adminsDecide`), as only they give an agent new access (ADR 0016); the decision and the job that resumes the run commit in one transaction. `executeApproved` re-checks the hash against the stored params, re-checks the scope (it may have been revoked while waiting), claims `executed_at` (never twice), and runs exactly the stored params. Refused or expired requests become an error tool result with the reason. A worker expires pending approvals every minute. Events `approval.created` / `approval.decided` go to the channel and to each approver's user topic.

**Runs as tool loops.** `agent_runs.transcript` holds the conversation sent to the model (system blocks, messages with neutral content blocks, pending tool calls) and is saved after every turn. It is append-only: a resumed run sends exactly the same history plus the tool results, which keeps provider thinking blocks valid and prompt caches warm. The executor loops model call → tool calls → results until the model answers or `AGENT_MAX_TOOL_TURNS` is reached. On a sensitive call it posts what the agent said so far plus one approval card per request (`messages.meta.approvalId`), saves the pending calls, and moves the run to `waiting_approval` in one transaction. A run resumes only when all of its approvals are decided.

## Consequences

- A retried job continues from the saved transcript. A crash between running a non-sensitive tool and saving can repeat that tool; sensitive actions can't repeat (`executed_at`).
- Tool results are capped at 50 000 characters for the model and 4 000 in steps.

## Addendum (2026-10-30): "Aprovar sempre"

A person who decides an agent's approvals may approve a kind of call for good, so the agent stops asking for it. The kind is the agent, the connection, the server's own tool name and each action that tool runs (Composio's executor, ADR 0016); never the params. Only a tool that names what each call does can be remembered: any other tool approved for good would run with any params (a raw request, a GraphQL mutation, code), so a custom server's other tools keep asking, and an admin who wants one to stop sets it to Escrever. Rules live in `approval_rules (org_id, agent_id, connection_id, tool, action)`, `action = ''` for the tool itself when a source remembers one that runs nothing else, unique per kind.

- **Offered** only where the gateway says so when it asks, stored on the request (`approvals.approve_always = { tool, actions }`, null = not offered): a run that isn't a routine's, whose policy didn't force the ask (routines and missions always ask; a run nobody is behind is offered it too since ADR 0053's addendum of 2026-10-31), a tool its source lets be remembered (`ToolDefinition.rememberAs`, on custom servers only the executor), with known wrapped actions none of them sensitive (`actionLevel`: a send, delete or payment in any word form, such as `SLACK_DELETES_…`, `GMAIL_REPLY_…`, `SLACK_CHAT_POST_MESSAGE` or `VERCEL_BUY_…`), and nothing in its names, scope or actions that matches merge, deploy or rollback, has a word starting with merge, deploy, redeploy, rollback, revert, restore, promote, workflow, build, dispatch, reference, release, alias, rolling, rerun or rerequest (a repository dispatch starts workflows, a reference moves a branch, an alias or a rolling release takes production traffic), has commit, trigger, run, execute or invoke right after its app, or is open-ended (`openEnded`: GraphQL, SQL, a proxy, a query it runs, whose arguments say what it does). Never on built-ins (mail has its own switch), catalog connectors, the code runners and Composio's proxy, or a high-risk card that takes a hold.
- **Deciding** is `POST …/approvals/{id}/approve` with `always: true`, by the same people as the approval (`mayDecide`). The rules are written in the decision's transaction, and the `approval.approved` audit row carries `always`. Where it isn't offered: 409 `approval.always_unavailable`.
- **Honoured** in the approval branch after the scope, schema, credential and argument checks and before the "say why" refusal: a covered call (one fresh query, no cache) runs like an allowed one, with its team action and a `tool.call` audit row with `details.approvalRules`. A rule never grants access: losing the scope, a denial or a tool turned off or sensitive stops it before any rule is read.
- **Undone** on the agent's page (Ferramentas e acesso, "Aprovado sempre", `GET`/`DELETE …/agents/{agentId}/approval-rules`) and on its profile on the phone (since 2026-10-31), by admins and the agent's owner, audited as `agent.approval_rule_removed`. Disconnecting the server and deleting the agent delete its rules.
- **Git targets** (2026-10-31, ADR 0024): a tool whose every call names one exact target (`ToolDefinition.rememberTarget`, only `request_branch_push`: `owner/repo:branch`, the repository in lower case) is remembered by its own name and that target, after the person and policy checks above and without the name checks written for connector actions, so a branch named release-x can still be approved for good. Only a call naming the same target runs without asking, and the git proxy reads the same rule as the grant to push there, unless `request_branch_push` is denied to the agent. Removing that rule also ends the earlier approvals of its branch. `delete_branches` never offers it.

## Addendum (2026-10-31): the step limit ends with Continuar, and screen steps count apart

A conversation run that reached `AGENT_MAX_TOOL_TURNS` failed with `too_many_tool_calls` and posted nothing: the person saw only a failed mark. Browser tasks hit it most, since each step is a model call.

- **Every run but a forum's is told to wrap up.** Two calls before the cap (`WRAP_UP_TURNS`) a model-brain run reads one note, once: a routine's run `WRAP_UP_NOTE` (ADR 0053 §10), any other `WRAP_UP_REPLY_NOTE` (say what it did, where it stopped and what is left). The note is a text block after the tool results, in the user message about to be sent for the first time: the history stays append-only and the thinking blocks valid.
- **At the cap a conversation run ends `done`.** Its reply is the answer it wrote after the note or, still mid-work, the line "I ran out of steps before finishing." (`bodyCode` `step_limit`) with what it changed and where it browsed. Either reply carries `meta.stepLimit`, and the apps show "No limite de passos · Continuar" under it. A routine's run still fails (its ledger says so), and so does a forum's turn or synthesis: the topic stalls and Retomar does it again (ADR 0022), so the line is never counted as the agent's post or published as the decision. At the cap the inbox is not read: a message that came in, even during the last call, gets a run of its own.
- **Continuar** (`continueRun`) also takes a `done` run whose reply has `meta.stepLimit`, once (`meta.stepLimit.continuedRunId`), for the same people as a stopped one. Who pressed it counts as who asked the new run (`runRequester` reads `continuedByUserId` from either mark): they may stop it, continue it again, and press "Responder agora" on it. The new run starts from the same conversation with its own count.
- **The same `tools` for a run and its continuations.** A thinking block is bound to the system prompt, the tools and every message before it: Claude rejects one replayed after a change to `tools` (a 400). `continuedTranscript` keeps the tool groups (ADR 0043), the "Automático" choice and `passListed`: `pass` is listed for good in a run that started able to pass, continuations included, and refuses once a person is owed an answer (a person wrote into it, decided what it waited on, or pressed Continuar). Tools that depend on what is available when the call is made (the browser and desktop while the computer is there, the permissions `request_permission` lists) can still change.
- **Screen steps count apart** (replaced the same day by the backstop below, where every step counts). A model call whose every tool call drives the browser or the desktop (by name, through `use_tool`, or with the bridge's `mcp__agentes__` prefix) and worked (no error result, no pause for a person) counts in `Transcript.screenTurns` instead of the cap, up to `SCREEN_TURNS_FACTOR` (2) times it: by default 25 calls plus up to 50 screen steps. A failing step, or a call that mixes in any other tool, counts toward the cap: a loop on a browser that isn't open stops at 25. The Model Gateway still checks the budget before every call.
- **What the count covers.** It is per run: an approval resume and messages read while it works don't reset it, and a call cut by "Parar e mandar" counts. Each Continuar is a new run.

## Addendum (2026-10-31): "Aprovar sempre" for actions through Composio

Amended by ADR 0107. A tool of a service through Composio runs one explicit action, so the connector source offers "Aprovar sempre" on it (`rememberAs`, the tool's own name, `create_folder`) when it asks only because of its level (an admin set it to ask, or the judge suggested it): never for a sensitive one, nor for an action whose name always asks (`alwaysAsks`: deploy, release, run, execute, trigger, a query). The rule is per agent and account, as for Composio's executor.

## Addendum (2026-10-31, later): the cap is a backstop, and runs that go in circles stop

25 calls stopped real work (posting on a few sites, a big refactor) and still let a loop spend 25 calls. A long task should finish without anyone pressing Continuar; only a run that is stuck or runs away should stop.

- **A backstop.** `AGENT_MAX_TOOL_TURNS` defaults to 200 (still at most 200), and every model call counts, browser and desktop steps included (`screenTurns` and `SCREEN_TURNS_FACTOR` are gone). The wrap-up note and the ending above apply only near and at it. Routines, forum turns and syntheses keep their endings there: a routine's run wraps up with `WRAP_UP_NOTE` and fails with `too_many_tool_calls`, a forum's fails.
- **Repetition, by structure** (`stuck.ts`, `noteStep`): after each step of a model-brain run whose calls all came back (a computer brain's own calls never reach the server), the step's calls (tool and canonical input) and results (spacing collapsed, every number masked, so times, ids and counters don't count) are fingerprinted, each call also with what it got back, and the last 8 steps are kept in `Transcript.stuck`. The thresholds (`STUCK`):
  - the same call 3 times in a row: one identical retry is normal (a flaky call, a page not ready yet), a third means nothing changed between attempts;
  - the same error 3 times among the last 8 steps, whatever the call: two tries at a fix are normal, a third time the same error means the changes don't reach its cause;
  - 4 steps in a row whose calls all failed: errors that repeat what was tried (a guessed path, a selector, a column) never match each other, and four such guesses in a row are variations that end the same way;
  - 5 steps in a row whose every call was already made among the last 8 and got the same back: going back to a page is normal, and a cycle needs a few rounds to show (A, B, A, B is caught at its 7th step). A new call that gets the same answer is new: a message sent to ten people ("Sent."), edits to one file, the next page of numbers.
  After a verdict only newer steps count, so a long poll is judged every few calls and never stopped by a count.
- **Jev decides, in any language.** Only on a sign is the judge asked, one question (`stuck_run`, `STUCK_QUESTION`) with the request (its first 1,000 characters), what repeats, and the 8 steps kept: each call's tool, input (200 characters) and the start of what came back (300), cut on whole characters (`cutText`: half of an emoji is a lone surrogate, which Postgres jsonb refuses). Stuck at 0.6 or more, as the other judgments that act. Jev answers, the workspace's small model when Jev is off or fails (`withJudgeFallback`), and when neither can, the sign is the verdict. Its usage is recorded like every judgment's (kind `router`, with the org, the agent and the run).
- **Stuck once: a note** (`STUCK_NOTE`: try a different approach, or say plainly what blocks it), appended the way the wrap-up note is. A forum's turn or synthesis reads `STUCK_FORUM_NOTE`, only the different approach: its last words are its post or the topic's decision, never a line on what blocks it. **Stuck again in the same run: it ends the step-limit way.** A conversation run reads `STUCK_END_REPLY_NOTE` (reply with what it did, what it tried and what is left) and has two more calls; that answer, or else the line "I got stuck and stopped before finishing." (`bodyCode` `stuck`), carries `meta.stepLimit.stuck`, and the apps show "Parou porque travou · Continuar" instead of "No limite de passos". A routine's run reads `STUCK_END_NOTE` (hand off what it has, then end with its record) and fails with `stuck` either way, which its ledger shows, with its record as the detail when it ended as told. A hand-off it made keeps the routine run `reported` (people heard it); otherwise a routine stuck on every firing counts failures, its creator hears of the first, and it is paused like any failing routine (ADR 0053 §6); a forum's turn or synthesis fails with `stuck` at once (the topic stalls for Retomar). Each verdict is a `context` step (`stuckCheck`: the sign, the verdict, who decided, what followed).
- **A person starts it over.** Reading a person's message to the agent, or resuming on what a person decided for it (an answer to its question, an approval, a secret), drops what was found, unless the run is already ending. Continuar starts a run with nothing found, and carries what the person asked (`Transcript.request`): the new run's trigger is its own stopped reply, so the stuck and follow-through judges read that request instead.
- **Costs stay bounded.** The Model Gateway checks the budget before every call and the stretch limits (ADR 0089) are unchanged; a stuck check is a fraction of the model call it follows.

## Addendum (2026-10-31): approved ahead

A routine's run has nobody behind it, so each write it makes to a connected app asks a person at that moment (ADR 0053 §2): a post someone scheduled for 10:00 sat at 10:00 waiting for an approval. Approving ahead keeps the rule that a person approves every sensitive action and moves when they do it: they approve the exact action when it is scheduled, for that time.

- **Prepared** with `schedule_action` (scope `schedule:write`; a person's run only, like the other scheduling tools in the run policy): the exact tool, its full arguments and the run it is for, `when` (a new one-off in this conversation, access `act`, made only after the call passed every check) or `routine` (the next run of one of the agent's routines that may act). The gateway checks the call as that run will make it (`prepareAhead`: a connected app's write that asks a person, the agent's scope, the input against its schema, no credential, the arguments' rules) and stores an ordinary approval bound to its hash, plus the run it covers: `approvals.routine_id` and `run_at` (that run's slot, the brief's `dueAt`). Its card goes where the person asked and says it approves a future action and when it runs. It expires by `run_at` at the latest, and within 24 h like any request. The run that asked waits for the decision as with any approval; once approved, `executeApproved` runs nothing and tells it when the action goes out.
- **Done at its time**: the routine's run reads in its brief what was prepared for it and calls `run_approved_action` with the id. The gateway turns that into the stored call, which then meets every check a direct call does (policy, scope, schema, credentials, arguments, the team's actions). In the approval branch, a call of that routine's run for that slot whose hash matches an approved approval not yet run goes out without asking: claimed once (`executed_at`, only while still approved), with its result, step and `tool.call` audit row carrying the approval, and its cards hear it ran (`approval.decided`, from `invokeWithChip`). This holds until `run_at` plus 30 minutes (`AHEAD_GRACE_MS`). Later, with any other content, from a manual run or from another routine, it asks a person as before. The latest decision on that exact call for that slot wins: a refused one never runs (the call is refused without a new card, and a one-off left with nothing to do no longer fires) unless a person later approves the same call again for that run, and one approved and then refused on another card doesn't run.
- **Never for merge, deploy, rollback and the rest**: only a connected app's own tools can be approved ahead (`ToolDefinition.ahead`, set by the connector source; never Composio's workbench, bash or proxy), with their wrapped actions known, and nothing in their names, scope or actions on the never-for-good list of "Aprovar sempre" (`alwaysAsks`: merge, deploy, rollback and the like, GraphQL, SQL, a raw request).
- **Changed means asked again**: other content is another hash. `schedule_action` with `replaces` withdraws the earlier one once the new one is asked (for the same run unless another time is given). A routine whose next run moves or goes (its time changed, paused), whose agent or access (down to read) changes, or that is deleted withdraws what was approved for it, and so does a one-off canceled as a reminder or run by hand before its time. An approved one its run didn't do by `run_at` plus the grace expires (the worker that expires requests).
- **Withdrawn** before its time from its routine's page (Preparado para depois, on the web and the phone), its card or its details: `POST …/approvals/{id}/cancel`, by whoever sees it (as on the approvals list) and may decide it or manages its routine, else 404 (status `canceled`, audited as `approval.canceled`). The routine's view lists what may still run (`ahead`), to those who read the routine, and only what each of them sees on the approvals list: the request lives where it was asked, which may be a private conversation.
