# 0116. Agents' git clones: straight from GitHub, apart from the request, two at a time, through a shared cache

- Status: Accepted (built for single-user runners; the per-computer queue and the shared cache on system-mode computers are left for later)
- Date: 2026-11-01
- Amends: ADR 0024 addendum (`git.sync`: fetches no longer have to go through the proxy; pushes still do)
- Code: `apps/server/runner/git.ts` (`directCredentialHelper`, clone jobs, `MAX_CLONES`, `CLONE_STALL_MS`, `fillCache`), `apps/server/runner/daemon.ts` (`gitCache`), `packages/engine/src/git/machine.ts` (`directFetchTokens`, `MACHINE_CLONE_WAIT_SECONDS`), `packages/engine/src/git/tools.ts` (`git_clone` on `cloning`), `packages/adapters/src/machine-protocol.ts` (`GIT_DIRECT_PROTOCOL` 35)

## Context

Agents cloned big repositories at about 100 to 130 KB/s: a 2 GB repository took hours, and several agents cloned the same ones. Every pack byte went through one Bun process on our app server (the git proxy, ADR 0024); each deploy (many a day) cut every clone in flight, and a clone never resumed; a fixed 30-minute deadline cut big clones anyway; partial clones later fetched blobs one request at a time through the proxy; and nine or more `index-pack` processes at once thrashed a 4-vCPU computer.

## Decision

1. **Fetch from GitHub, push through the proxy.** Where our GitHub App is installed for the repository and the agent was given it, a runner on protocol 35 gets, with each `git.sync`, a GitHub App installation token for that repository alone with `contents: read` (GitHub's tokens last one hour; the server's cache hands out one until 5 minutes before it ends). The checkout's `remote.origin.url` is `https://github.com/<owner>/<name>.git` and `remote.origin.pushurl` the proxy, so every push is still checked there (only `agentes/<handle>/…`, the agent's repositories). One credential helper, in the checkout's own config after the machine's are reset, hands the GitHub token (its own file, mode 600, in the runner's or the agent worker's private folder) only to `github.com` and our proxy credential to every other host. Each turn's sync and each `git_clone` hand over a fresh token, so the agent's own `git fetch` keeps working. The connection's own token (OAuth or pasted) never reaches a computer: without the App, fetches go through the proxy as before, and a sync without a token puts the checkout back on the proxy.
2. **A clone outlives its request.** The runner runs each clone as a job apart from the request: a socket that drops (a deploy) doesn't stop it. The server waits up to 10 minutes; past that the answer is `cloning` with git's last progress line, and `git_clone` tells the agent the download goes on by itself and to call it again when it needs the code. A later `git.sync` of the same folder (the agent's next `git_clone`, or the sync before a turn) waits for the same job and never touches the half-made folder. The fixed deadline is gone: a clone stops when git shows no progress for 10 minutes (with a 24-hour ceiling). An older runner keeps the 30-minute deadline.
3. **At most two clones at once per runner.** The others wait in order; their answer and progress say "waiting for another download to finish".
4. **A shared read-only cache (single-user runners).** Before a clone, the repository is fetched into `<runner home>/git-cache/<connection>/<owner>/<name>.git` (a bare repository, one fetch at a time per repository) with the requesting agent's own credentials, so it reaches only what that agent may fetch; then the checkout is cloned whole (no blob filter) with `--reference` to it, so only what the cache lacks comes over the network. The cache never prunes (`gc.pruneExpire=never`, cruft packs, no `--prune`), since checkouts borrow its objects, and nothing removes a cached repository yet. Without the cache the clone is partial (`--filter=blob:none`) as before.

## Consequences

- The app server carries only pushes and what goes through the proxy without the App; deploys no longer cut downloads.
- A GitHub App token the agent's checkout can read reaches the computer: one repository it already has, read only, for an hour. The agent could read that repository through GitHub's API in that hour without our audit; it could already clone it.
- Left for later, with the reason: on a system-mode computer (every Cloud computer) each agent's git runs in its own worker process as its own OS user, so the queue caps clones per agent there, not per computer, and the shared cache is off. Both need a root-side clone service in the supervisor: the cache as `/var/cache/agentes-git/<connection>/<owner>/<name>.git` owned by a system user `agentes-git`, fetched under `flock` with the agent's credentials, with a per-agent read ACL on each repository it fetched, and the slots as `flock`ed files every worker shares. Removing a cached repository once no `objects/info/alternates` points to it comes with that.
- A clone killed with the runner leaves its folder; the next sync treats it as a checkout and fetches into it (git resumes no pack mid-way).
