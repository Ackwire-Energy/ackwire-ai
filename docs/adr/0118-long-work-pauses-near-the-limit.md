# 0118. Long work pauses near a plan's or a budget's limit

- Status: Accepted (built: the server, the web and the phone app; the runner is unchanged)
- Date: 2026-11-01
- Builds on: the usage-aware design's Phase 1 (a run at the limit waits in its own session and resumes by itself, `usage-pause.ts`), ADR 0097 (the continuation controller), ADR 0089 (the stretch card's look and its Continuar)
- Code: `packages/ui/src/plan-state.ts` (`PLAN_PAUSE`, `PLAN_NOTICE`, `planBinding`, `extraUsageOn`, `extraUsageLeft`), `packages/engine/src/usage-pause.ts` (`isLongWork`, `budgetUsedPercent`, `usageNoticeText`, `continueUsagePause`, `usageCardResumed`), `executor.ts` (`usageReading`, `longWorkPause`, `postUsagePauseCard`, `waitForUsage` with `usage_pause`), `run-hold.ts`, `steering.ts`, `brains/select.ts` (`sessionFor`), `no-ai.ts` (`answerNow`), `brain-settings.ts` (`extraUsage`), migration `0172_long_work_extra_usage`, `packages/client/src/lib/usage-pause.ts`, web `UsagePauseCard.tsx` and Quem pensa, phone `UsagePauseCard.tsx` and Pensa com

## Context

Phase 1 made the limit itself safe: a turn the plan refuses parks and picks up after the reset. But long work (a routine, a mission, a run that took many steps) still ran straight into the limit, and then everything on that plan stopped, quick replies to people included, for hours or, on a weekly window, for days. The owner's decisions (2026-11-01):

- **A1** One pause line at 95% for all long work, on every window (5 hours, week, a model's week, month) and on an API agent's monthly budget. Agents see where they stand from 90%.
- **A2** When the account's paid extra usage is on, long work may use it, with a switch to turn that off, shown only where extra usage can be seen.
- **A3** Continuar agora for the agent's owner, admins and the person who started the work; everyone else sees it greyed with the reason.
- **A4** Weekly and monthly windows pause long work too.

## Decision

1. **The gate is a pure function.** `planBinding(usage, { model })` is the most used window that applies to the run and still counts now: a window whose reset passed reads 0, one with no reset stops counting once its length passed since the reading, a model's own week (`seven_day_opus`, `seven_day_sonnet`, and Claude's `model_scoped` weeks, stored as `other` with the model's name) counts only for that model, and extra usage and OAuth apps never count. Nothing known means no pause: a reading only grows inside its window, so a stale one makes a pause late, never wrong. On the model brain the gate is the agent's budget this UTC month: spent / its effective budget (`budgetUsedPercent`, read only once the run is long). Over the line only with other calls' reservations in flight (worst-case, released in seconds), it parks quietly and looks again soon (Phase 1's ladder), never until next month.
2. **Long work** (`isLongWork`): a routine's slot (not Rodar agora, which a person just asked for: `routineRunByHand`), a mission's run (one woken by the mission's notices: a person's message in its thread starts a quick reply), or a run that grew in this claim of it: 8 model calls, a computer brain's third turn, or 10 minutes with a call made. A person acting on the run (an approval, an answer) starts a new claim, so a fresh allowance. A run that paused once stays long. Replies, colleagues' quick answers and forum turns stay quick and run until the plan's own limit.
3. **Where it stops: the loop top, one place for every brain.** Before each step (after steering is read, so nothing a person sent is lost) a long run at 95% or more parks. On the model brain nothing is in flight and the transcript ends with tool results, so the resume replays it. On a computer brain it is between turns: a pending next prompt (a steered message, the controller's nudge) moves to `transcript.continued` and is read on the resume. Turns in flight are never stopped (Phase 3 if events show overshoot). A run's first loop top is its start, so a routine's slot at 95% parks before any turn.
4. **The continuation controller is untouched.** It still decides how a turn ends; its `continue` reaches the loop top like any next step, where the gate parks it. A paused run is never ended `done` (nothing would bring it back) and its stuck detection and stretch are unchanged.
5. **Parking reuses Phase 1's wait.** `waitForUsage` with code `usage_pause` and `waitingForBrain.source` (`plan` or `budget`): `waiting_input`, the timed `agent_run.execute` job at the window's reset (or the next month) plus the stagger per plan or budget, re-parked quietly while still at the line. A budget raise resumes it (`resumeBudgetWaits`), the computer coming back doesn't, and the next routine slot supersedes a paused one (`waiting_plan` / `waiting_budget`). The agent's status reads it as waiting for its plan or budget.
6. **The card.** A conversation run posts one card where it answers, as the agent (`meta.actionCard` `usage_paused`: run, wait id, source, percent, window, plan, reset, who is behind the work). A routine's run posts no card, as in Phase 1: its creator and the agent's owner hear it once per outage (`routine_waiting_plan`), and Rodar agora on it runs it now (a manual run isn't long by kind and supersedes the paused slot), and Rotinas shows it paused with Continuar agora (point 7). Picking up by itself turns the card to "retomou o trabalho"; a re-park is silent. A run that ended while paused (canceled, failed) turns its card to `ended` when someone presses Continuar agora.
7. **Continuar agora** goes through `answer-now` (`continueUsagePause`): who may stop the run may press it (`mayStopRun`: who asked, the person behind the work, the agent's owner, an admin; 403 `run.answer_forbidden` otherwise). A compare-and-set on the wait id with no override yet sets `usagePause.override` until that window resets (the plan's own limit still stops it) and queues the run; a second press, or the timed job first, does nothing. Audited as `usage.continued`. The apps grey the button for anyone else and say who may press it.
   **On Rotinas** a routine's paused slot reads as the quiet state `usage_paused` ("Pausada até 14:00 (limite do plano)", `RoutineView.usagePause` with the reset kept in `waitingForBrain.resetsAt`), in its row and its detail, until the reset passes or someone continues it. Its Continuar agora (`POST …/routines/{id}/continue`, `continueRoutineUsagePause`) is for the routine's creator, the agent's owner and admins (`routine.editor_only` otherwise); it shares `overrideUsagePause` with the card and posts nothing. A plan pause on an agent whose extra-usage switch is off is refused (`routine.continue_extra_off`), and the apps grey the button with that reason.
8. **Messages during a pause.** A person's message gets a quick run of its own (`holdsMessages` includes `usage_pause`, and steering doesn't wake the paused run), so the reserve goes to replies. A mission's notices queue on its paused run and are read when it picks up (`enqueueRunJob`). That run never takes the session of a run still waiting (`sessionFor` skips `waiting_input` and `waiting_approval` runs).
9. **Paid extra usage** (`agents.brain_extra_usage`, default on, migration 0172). Long work doesn't pause while the account reports extra usage on, its own cap is under 95% used (`extraUsageLeft`), and the agent's switch is on. The switch shows whenever extra usage is reported (`extraUsageOn`). What each provider reports:
   - **Claude** (Pro, Max, Team): `get_usage` returns `extra_usage { is_enabled, utilization, monthly_limit, used_credits }`, and a turn's `rate_limit_event` carries the `overage` window. The runner already stores both as an `other` window labeled "Extra usage" (only when enabled), so the server sees it with no runner change. The switch shows only there.
   - **Codex / ChatGPT plans**: `account/rateLimits/read` returns `credits { hasCredits, unlimited, balance }`; the runner doesn't read it yet, so no switch. Adding it is a runner change (the Cloud pin).
   - **Cursor**: not a brain here; its spend limits and on-demand usage have no API we read.
   - **Z.ai**: the usage endpoint reports the 5-hour, weekly and monthly quotas but not whether extra usage is on; only the refusal codes 1316 to 1321 say it is unavailable. No switch.
   - **Kimi, OpenCode Go, MiniMax**: Extra Usage or credit packs exist, none is reported by the endpoints we read. No switch.
10. **What the agent knows.** From 90% of its plan a computer brain reads "# Your plan's usage" in "# This turn", refreshed on every claim: where the plan stands, that long work pauses at 95% and picks up after the reset, and to say so before starting something big (or that extra usage lets it go on). It is never told to stop by itself.

## Consequences

- No runner change, no new job kind, no env var. One column (`agents.brain_extra_usage`).
- Not built from the design (each is a small follow-up if events ask for it): the wrap-up note before a model-brain pause (it parks at the next step instead, the card says where), the resume line ("the plan has room again…"), waking paused runs at once on an early reset reading (they wait for the timed job), the push per account and reset, the API-fallback line under a reply, the budget notice at 90% on the model brain (`get_my_usage` answers it), the runner's 95% `usageCrossed` line and its probes during a turn.
- A shared or lent Claude sign-in reports usage only at a few moments, so a long turn there may still run from 90% to 100%; Phase 1's wall is the backstop.
- 8 calls, 3 turns and 10 minutes are starting values, to be set just above the p90 of reply runs from production's 30-day query.

## Addendum (2026-11-02): Continuar agora with extra usage off

The owner's decision for Phase 2: with paid extra usage off, Continuar agora on a run paused at 95% goes on up to 100% of the plan's window, the plan's own allowance. It is refused only when going on would pass 100% with extra usage off (the plan's window is used up and the agent's switch is off, or the account's extra usage is off or at its own cap), and the refusal says so and that the run picks up after the reset. One rule for every place: `continuesPastPlan` (`usage-pause.ts`) over the plan's reading now, read again from where the run parked (`waitingForBrain.reading`: computer, account, model), through `pauseContinuesPastPlan`. The chat card refuses with 409 `run.continue_extra_off`, Rotinas with 409 `routine.continue_extra_off`, and Rotinas' `usagePause.extraOff` (the greyed button) is the same check. When the agent's switch is on but the plan has no extra usage left (none reported, or its own cap at 95% or more), the same check refuses with `run.continue_extra_used_up` / `routine.continue_extra_used_up` and `usagePause.extraUsedUp`, whose words don't send the person to a switch that is already on. A budget pause is never refused here. After a press the gate still applies the rule: a continued run with extra usage off parks again at 100% instead of going on into paid extra usage, as a new pause.

## Addendum (2026-11-02): waits that always end, say what they wait for, and can be canceled

A routine's daily slot hit the plan's limit before a reset; a person's reply on the same plan picked up right after the reset while the slot still read "Running" and the agent's status still said it waited for the plan. Two ways a parked run could outlive the reset, both closed at the shared points:

1. **Each wait had only its own timer.** A run parked with a later or unknown reset (a stale reading, an unknown reset's re-checks at 2, 15, 30, 60 minutes) slept on even after another run had gone through on the same plan. Now a computer turn that goes through (no `limit` event in it) forgets the limit cached in the process and wakes every run parked on that plan's limit (`plan_limit`, same `waitKey`) now, in `usageWaitPlace`'s order, 60 s apart (`wakePlanWaits`). A pause near the limit (`usage_pause`) keeps its timer: a quick reply going through says nothing about its 95% line.
2. **A wait whose job was gone waited forever.** The recovery sweep now wakes any usage wait past its `until` with no live job (`recoverStaleRuns`); still limited, it parks again quietly.

The agent's status moves as soon as a run comes back from any wait (`announceAgentStatus` at the claim), not at the apps' next refetch.

**What it waits for, everywhere.** Every usage wait stores its reset (`waitingForBrain.resetsAt`) and plan name (`plan`). Rotinas shows a slot waiting on its plan or budget as `usage_paused`, at the limit too (`usagePause.limit: true`, no Continuar agora there), until it picks up (past the reset as well), worded "Waiting for the Claude plan · runs at 9:00 AM"; its run in the timeline is `waiting` with `waiting_plan` / `waiting_budget`. The plan's name is the provider-general one (`planName`).

**Don't run it.** Whoever may stop the run (`mayStopRun`) cancels a waiting run where the wait shows: the agent's "I'll answer when it resets" note (`meta.usageWait.runId`, `forUserId`), the long-work card, and Rotinas' Parar, worded "Não rodar" there (the routine's creator, the agent's owner, admins). It is `cancelRun` / `stopRoutineRun` as before; stopping a run that waited on usage marks its note `usageWait.canceled` and its card `canceled` ("Cancelado. Não vai rodar quando o limite voltar."). The long-work line keeps its Parar.

## Addendum (2026-11-03): one limit note per conversation, and receipts that say the wait

In a DM an agent said "O plano do Claude chegou ao limite. Respondo às 18:30, quando ele renovar.", the person pressed Não rodar, wrote again, and five minutes later got the same note again. The receipt on their message read "Esperando sua resposta", as if the agent had asked them something.

1. **One note per agent, conversation, person and wait** (`joinUsageNote`, `usage-pause.ts`). A turn parking on its plan's limit or its budget for the first time posts no note when the agent's word in that conversation (the DM's or channel's main timeline, or the thread; notices the agent reads don't count) since it last said anything else holds a usage note to the same person (`usageWait.forUserId`), with the same code and the same reset (within a minute, or both unknown), whose run isn't back at work. Per person because only who asked (or the agent's owner, or an admin) may stop a turn: a note shared by two people's turns would offer one of them a Não rodar they can't press. In a channel where Ana and Bia both ask, each gets one note. A note still waiting takes the turn in (`meta.usageWait.runIds`), and its Não rodar reads "Não rodar estas 3" and stops every turn it speaks for, each for who may stop it (`cancelRun` follows `stopRun`'s `joined`). A note cancelled less than 15 minutes ago (`CANCELED_NOTE_QUIET_MS`, `usageWait.canceledAt`) stays as it is and the new turn shows only its receipt; after that, or with another reset, the turn posts its own note. A turn cut mid-work keeps its own "Parei no limite" note. Language-neutral, web and phone alike. This is the small part of the per-conversation catch-up design: when plan and budget waits take later messages into the same run, the note stays one by construction and `runIds` stays empty.
2. **Receipts say the wait.** A run waiting on usage carries `usage: "plan" | "budget"` in its receipts (`usageWaitSql`, `runs.ts`) and in `agent.run`, `run.finished`, `message.handled` and `agent.run.steered`. The shared receipts read it as the phases `plan` / `budget`: a line under the message ("Ada responde quando o plano renovar"), "Responde quando o plano renovar" in the popover and the phone's sheet. "Esperando sua resposta" stays for a run that asked the person something. A run canceled once started reads `canceled` ("Ada não vai responder", "Cancelado"), not "Respondeu"; canceled before it started is still "Não respondeu". Long work paused near a limit (`usage_pause`) reads the same by its source. No time in the receipt: the note above says it.
