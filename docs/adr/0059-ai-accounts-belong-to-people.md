# 0059. AI accounts belong to people: one account per agent, a plan answers its owner, more providers, official marks

- Status: Accepted (2026-10-24). Built in steps; the provider marks (§9) first. Amended 2026-10-27: §2 and §4 (one login per agent), §5 (plans are personal where the server provisions the computers); 2026-10-28: §6 (no address asked); 2026-10-29: §5 (in every setup the plan's owner lets its agent reply to everyone, with nothing to accept); 2026-10-30: §2 (Claude's sign-ins are one login per agent), §3 (the computer's own sign-in on a computer nobody connected), §4 (automatic names leave the plan out, and Claude's plans go by Anthropic's names), §5 (the switch's words, and a line that says whom the agent answers)
- Date: 2026-10-24
- Extends: ADR 0018 (providers), ADR 0027 (secrets end to end), ADR 0032 (computer brains), ADR 0041 (accounts per agent)
- Supersedes in part: ADR 0041 §2 (who adds accounts), §4 (who decides) and §7 (removing); ADR 0032 §5 (when the plan warning shows); ADR 0058 §4 (who drives an agent's computer in system mode while its user holds a sign-in)
- Out of scope for now: accounts switching by themselves, a fourth CLI brain, Chinese regional endpoints

## Context

ADR 0041 put Claude and ChatGPT subscriptions on a connected computer, one folder per account, managed only by the person who paired the computer. Three things changed:

- **Computers without a person.** A Cloud workspace's machine and a self-hosted server's own computer have no pairer, yet every member wants to bring their own plan to them.
- **Several seats per person.** A team plan gives one person several seats. With labels such as "Claude Max · Max" nobody could tell the rows apart, or whose account served which agent.
- **Sharing a personal plan.** ADR 0032 warned once, when a plan brain was chosen, and after that the agent answered whoever its audience allowed, on one person's subscription.

People also asked for more providers than Anthropic and OpenAI (DeepSeek, Kimi, Z.ai's GLM, MiniMax, OpenCode), for the providers' official logos wherever a provider is named, and for each plan's usage limits on screen.

## Decision

### 1. An account belongs to the person who added it

- The owner is bound when the sign-in **starts** (the row is written then, with the caller as owner), never inferred later from who polled first. Only the person who started a sign-in may send its code, check it or cancel it.
- Accounts the desktop app reports with no sign-in started from the web belong to the computer's pairer. On a computer with no pairer they have no owner: nobody assigns them, and the pairer or an admin can remove them.
- Only the owner sees the account's email, renames it, assigns it or signs in to it again. The computer's pairer can disconnect any account on that computer; on a computer with no pairer, so can admins.
- **Who adds:** any member on a computer with no pairer (the Cloud machine, the server's own computer). On a personal computer only its pairer adds accounts, as before: other people's sign-ins on someone's laptop raise a consent problem, and they would outlive the computer if its token were revoked.
- A person who leaves the organization or deletes their account has their accounts signed out and removed from every computer, with a tombstone until the runner confirms. They are never inherited by anyone.

### 2. One account thinks for one agent

- An account serves at most one agent (a unique index). Picking an account another agent uses offers to move it here.
- The computer's own sign-in (no folder) can still serve several of its pairer's agents.
- Each seat's limits stay predictable, and on a computer where every agent runs as its own OS user, one sign-in folder can't be shared anyway.

*Amended 2026-10-27:* one login (a row and its folder) still serves at most one agent, and an account may have one login per agent where `LOGIN_PER_AGENT` (`packages/providers/src/plans.ts`) allows it. "All agents" then signs each agent in with the same account, back to back, and a coding plan's key is pasted once and sealed to each login. The coding plans allow it now: a key has no refresh token, so its copies never sign each other out, and several agents of one person are still one user of the plan. Claude's and ChatGPT's sign-ins stay one agent per account until several sign-ins of one account are seen to hold through their refreshes. Users report that a new Claude sign-in can sign the account's other sign-ins out (anthropics/claude-code #20310, #40419, #80292), and OpenAI documents one `auth.json` per runner or serialized job stream. Each turns on by flipping its value.

The plan's panel says whom it is for ("For [All agents ▾]"). "All agents" means the person's agents with no AI on one computer, and those already on that plan. An agent on the API key stays out, since a plan would make it answer only its owner, and one on another plan keeps it. The setup opens on "All agents" where the plan allows it. Elsewhere the panel opens on the agent it was opened for, else on "All agents" while two or more have no AI, else on the first with no AI. One key fanned out to many agents counts each login against the ten sign-ins a person starts per computer every 15 minutes.

*Amended 2026-10-30:* Claude's sign-ins are one login per agent too (`LOGIN_PER_AGENT.claude_code`), so one Claude account thinks for several of its owner's agents. Signing in for an agent with an account another agent uses gives that agent a login of its own under the account's name: in Connect an AI for one agent, in the setup's AI step and with "All agents" (one sign-in per agent, back to back, the first one's email the next ones' hint), and from the agent's page, which offers such an account as one more login for this agent ("Also used by Ada") instead of moving it. A new sign-in of an account its owner already has on that computer is no longer refused for Claude; §6's refusal now holds for ChatGPT, which stays one agent per account. Signing in again as another account is still refused for both. Renaming one login renames them all, and removing one leaves the others thinking for their agents.

What to watch for: users report that a new Claude sign-in or a token refresh can sign the account's other sign-ins out (the issues above). A login signed out this way finds out at its next turn, when Claude's endpoint refuses it. The runner then marks it refused, and it reads as signed out whatever the CLI's own status says, until a sign-in there succeeds. The agent says its AI is signed out (its no-AI card, `not_signed_in`), and its page and Settings › AI accounts offer Sign in again for that login. No other login stands in by itself. If logins keep signing each other out, signing one in again may sign another out.

The fallback is setting `LOGIN_PER_AGENT.claude_code` back to false: a new sign-in of an account already on that computer is refused again, as before, and the logins made meanwhile keep thinking, each for its agent, until they are removed. On a computer the person connected, the computer's own sign-in still thinks for all of their agents there.

### 3. A plan only serves its owner's agents

A personal plan thinks only for agents owned by the plan's owner. This is checked when an account is chosen, when an agent changes owner (the plan is cleared), when an account goes away (the agent goes back to the API, or waits with no AI), and at run time (`plan_not_owner`, which also covers an owner who left). Runs never slip onto someone else's plan.

*Amended 2026-10-30:* on a computer nobody connected (the Cloud workspace's; the server's own computer is its owner's) the computer's own sign-in is nobody's plan, so it never thinks for an agent there. Such an agent's run reads it as not signed in (`not_logged_in`, ADR 0041 §1) instead of `plan_not_owner`: it fails at once with no AI and Connect, rather than waiting for a computer whose coming back would change nothing.

### 4. Labels people recognize

Automatic names are the maker and the plan, numbered per owner: "Claude Max", "Claude Team 2", "ChatGPT Plus", "GLM Coding", "Kimi Code", "MiniMax", "OpenCode Go". The owner sees the email under the name (and the organization of a team seat); everyone else sees "Claude Team 2 · {owner}'s" and never the email. The same email twice for one owner on one computer is refused, and the new folder is removed.

*Amended 2026-10-27:* where the account may have one login per agent (§2), the same account again is another login: it takes the account's name, and renaming one renames them all. Logins of one account are told apart by its email (in any case) or its key's last 4, never by the name, which any rename can repeat, and the apps show them as one row.

*Amended 2026-10-30:* an automatic name leaves the plan out: "Claude", "ChatGPT" or the coding plan's name, numbered per owner ("Claude 2"). The apps show the plan once, beside the name ("Claude · Max"), from what the computer last said, so an upgrade or a renamed plan never leaves a name that says another plan; a computer's own sign-in reads the same way by its maker ("Claude · Max"), and a name that already says its plan (as servers before this amendment name accounts, which the phone still meets) isn't followed by it again. Anthropic renamed its plans that day: Max 5x is Max and Max 20x is Ultra (claude.com/pricing). Claude Code's `auth status` says `max` for both, so the runner tells Ultra apart by the organization's rate-limit tier that the CLI writes at sign-in into the account folder's `.claude.json` (`default_claude_max_20x`); where the CLI couldn't fetch it, an Ultra reads as Max. A folder that was lent to an agent's user (system mode) never runs a CLI as root again, so its plan comes from that file alone (the organization's type and tier, one of the plans' words whatever that user wrote there), and an Ultra stored as Max before the rename becomes Ultra at the next look, with no new sign-in. Automatic names given before ("Claude Max", "Claude Team 2") became "Claude", numbered per owner, oldest first (the `claude_account_names` migration); a name someone chose stays.

### 5. "Only replies to you"

- An agent that thinks with a personal plan answers only its owner by default: the audience is `owner`, enforced everywhere a person's message can start a run (ADR 0032's audience gate).
- Turning the switch off shows the provider's own words about personal use and that answering others might go against its terms. Accepting sets the audience to everyone and is audited with the date. Choosing a plan no longer asks anything; only sharing it does.
- Only the plan's owner can widen the audience of an agent that thinks with their plan. Admins can only narrow it.
- With sharing on, anyone who can talk to the agent can make it use the owner's plan and, on a computer where agents share one OS user, reach its sign-in.
- A plan also picks who answers its owner's own messages nobody mentioned, only on a self-hosted server, and never for anyone else's (ADR 0074 §3).

*Amended 2026-10-27:* where the server provisions the workspaces' computers (`MACHINE_PROVISIONING=external`, the Cloud), the service runs the plans' CLIs for its customers, and the providers' conditions for platforms that do want each person on their own plan ("Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential", code.claude.com/docs/en/legal-and-compliance). There an agent on a plan answers only its owner whatever its stored audience, and nobody can widen it (`plan.personal`). An agent shared before narrows, and answers its stored audience again once it moves to the API key. A self-host keeps the switch and the warning: whoever runs it carries the terms.

The apps say it where it matters. The plan's panel ends with who the agents answer ("On your plan, Ada only replies to you."). Where every agent with an AI answers only the person setting up, the setup's Team step says so before anyone is invited, since someone invited then has no agent to talk to. On the Cloud the agent's page shows "Only replies to you" as a fixed line, with no switch.

*Amended 2026-10-29:* every setup allows it, the Cloud included, and nothing asks to accept the terms. The switch is "Replies to everyone" ("Responde a todos"), off by default: an agent on its owner's plan replies only to them until they turn it on, then to everyone its own "who can talk" setting lets in. A switch onto a plan still starts owner-only, only the plan's owner turns it on, and admins only narrow. Under the switch a short line says the plan's terms are a gray area here ("A gray area in Claude's terms", ChatGPT's, or the plan's for a coding plan), and its ⓘ says what they say, for a plan or for a seat. Turning it on or off is audited as any change of who may talk to an agent (`agent.audience_changed`), and nothing records an acceptance. The 2026-10-27 rule for the Cloud is gone (`plan.personal`): the gate reads the stored audience everywhere. The API still takes `acceptPlanTerms`, which older phone apps send, and ignores it. The confirmation dialog, the panel's fixed note and the Cloud's fixed line give way to the same switch, line and ⓘ: in the plan's panel (the setup's AI step and Connect an AI, for one agent or for all of them) and on the agent's page, on the web and the phone. Someone who isn't the plan's owner sees whom the agent replies to and who decides. Before a sign-in the panel's switch waits, and the move onto the plan carries it.

*Amended 2026-10-30:* people read the switch and its ⓘ and still didn't know what it did: "Responde a todos" reads like email's reply-all, and the line under it spoke of a risk, not of the switch. Only the words and the line change; every rule above stands. The switch is "Answers other people" ("Atende outras pessoas"; for every agent of a plan's panel "Answer other people", "Atendem outras pessoas"). The line under it says what the switch does in its current state, with the agent's name and the plan: off, "Ada answers only you, on your Claude plan." ("A Ada só atende você, pelo seu plano do Claude."); on, "Ada answers anyone who can talk to her, on your Claude plan." ("A Ada atende quem pode falar com ela, pelo seu plano do Claude."); for every agent "They answer only you…" and "They answer anyone who can talk to them…". A seat says "your Claude seat" and a coding plan its own name ("your GLM Coding plan"). The terms move behind that line's ⓘ ("About the plan's terms"), in plain words: "Claude plans are for personal use. Letting other people use yours is a gray area in Claude's terms." ("Os planos do Claude são para uso pessoal. Deixar outras pessoas usarem o seu é uma zona cinzenta nos termos do Claude."), each seat being for one person, or a coding plan's maker's own words, in the same shape. Someone who isn't the plan's owner sees "Answers only João" ("Só atende João") or "Answers other people", with "Ada thinks with João's plan. Only João can let other people talk to her." ("A Ada pensa com o plano de João. Só João pode deixar outras pessoas falarem com ela."), which is also what "Who can talk" says when an admin tries to widen it. The toasts, their buttons, the refusal, the note before inviting and New agent's note on a plan use the same verb ("answers", "atende").

### 6. The sign-in code never passes through our servers in the clear

ADR 0041's path stays: the provider's own CLI signs in on the computer, the pasted code is sealed in the browser to a key made inside the runner (ADR 0027), and the server relays the ciphertext in memory, never storing or logging it. Claude's flow uses PKCE (S256), so a relayed code is useless without the verifier that never leaves the CLI. The paste is the only hard step: the sign-in opens in a popup, "Paste" sends by itself only when the text ends with this sign-in's state, and an optional "Which account?" email becomes the CLI's login hint (validated, never passed to a shell). Each sign-in runs the provider's CLI on a computer others may share, so a computer runs at most four at once and a person starts at most ten per computer every 15 minutes.

*Amended 2026-10-28:* the apps ask for no address: the account chosen on the provider's own page is the one connected. The API still takes the optional email (older phone apps send it), and signing in again to a signed-out account sends that account's own email as the login hint, unseen. A new sign-in that comes back as an account its person already has on that computer is refused as before, and the answer now carries that account, which they may think with instead for an agent while it is signed in and no agent thinks with it. Signing in again that comes back as another account (an email other than the account's own, or one its person already has there) is refused too: the account stays signed out with its agents, never removed, and the answer says which account came back (`signedInAs`). That login stays in the account's folder until it signs in again or is removed; nothing thinks with a signed-out account.

### 7. Usage limits, read without touching a token

Each account's usage comes from the CLIs themselves: the rate-limit events during turns and a usage request that makes no model call (Claude Code), the app-server's rate-limit calls (Codex), and the provider's usage endpoint for a coding-plan key, called from the computer. The server keeps percentages and reset times only. The meter shows each window, tightest first, warns at 80% and says until when an account is at its limit. Accounts never switch by themselves.

### 8. More providers, on the right side of their terms

- **API keys** (pay per use, the workspace's): DeepSeek, Kimi (Moonshot), Z.ai (GLM) and MiniMax join Anthropic and OpenAI through the Model Gateway, all four through the existing Anthropic-Messages adapter with a base URL, sent only what they all take; structured output becomes a tool, forced where the provider honors `tool_choice: any` (DeepSeek, Kimi) and offered where it takes only `auto` (Z.ai, MiniMax). Usage and cost are recorded per agent as for every model call. *Amended 2026-10-27:* Gemini joins through its own adapter on Google's Interactions API (ADR 0018), with an API key only: Google's AI Pro and Ultra plans are served through Antigravity, whose terms forbid using the service in other products or through third-party tools.
- **Coding plans** (GLM Coding Plan, Kimi Code, MiniMax, OpenCode Go) run only on a computer, through Claude Code with a base URL, as a "key account". The key is sealed to the runner like a sign-in code and kept in the account folder; base URLs come from the runner's own plan list and are pinned in the runner's own settings file, which outranks project settings an agent could write. The plans' terms allow only coding tools, so our server never holds, routes or sees a plan key.
- A key account's turn gets the key in the process environment only (redacted from everything the runner sends) and keeps Claude Code's model aliases, each mapped to the plan's own models; no CLI signs in or out there, and a key its endpoint refuses reads as signed out until a new one comes. A sign-in account's turn pins Anthropic's own endpoint the same way, and a turn on the computer's own sign-in pins the endpoint, cloud and proxies the runner itself runs with (unless the computer's owner chose to load their own Claude Code settings). *Amended 2026-10-30:* a plan offers every model of it that answers through Claude Code, not only the ones its aliases name: the plan list holds each one with a tag from its plan's or maker's own words (cheap, fast, flagship), the alias it runs for, if any, what the plan's account must allow before it answers (OpenCode's Global region, for DeepSeek's models) and, on a plan that sells several makers' models, its maker, by which the pickers group them, as each maker documents them (OpenCode Go: 24 models, Kimi Code: 6, GLM Coding: 2, MiniMax: 1; OpenCode Go's free models and the ones that train on what they are sent stay out). The aliases keep the documented defaults, so "Automático" still maps its tiers through them, and Claude Code's `fable` alias runs the plan's `opus` model. A model with an alias is chosen and stored as that alias; any other as its id, which the turn passes as `--model` (its subagents too). A plan's model kept while another account thinks for the agent (another plan, Claude's sign-in) runs that account's `sonnet`: the engine maps it per turn and the runner again for its own plan, so an older runner runs the plan's `sonnet` model for an id it doesn't know.
- Account folders are secret paths for agent file operations, and environment names reserved for providers and the runtime are refused as agent secrets.
- Where each agent runs as its own OS user (system mode), account folders live outside root's home and belong to the user of the agent that thinks with one only while it does: handed over before its first turn (from a tree only root can change, its top last), and taken back to root as soon as the agents frame no longer says so (top-down, each folder root's before it is read, never through a link). Root never runs a CLI against a folder an agent's user could write: its status is what its turns said, signing in again starts it over, and removing it signs nothing out.
- While an agent's user holds its owner's sign-in, controlling its desktop or opening its terminal (a shell as that user, ADR 0058 §4) is only the agent's owner's: admins drive it again once it thinks with something else. Watching it stays as it was.

### 9. Official marks, next to the provider's name

- The makers' marks are vendored as 24×24 path data in `packages/ui/src/brand/marks.ts`, each taken from the maker's own files (a press kit, a brand page, or its repository at a pinned commit), which every entry names. A mark can add shapes in fixed colors (Kimi's dot, OpenCode's block, with the maker's dark color where it has one) and a gradient (MiniMax). The `anthropic` provider draws Claude's mark: people know it as Claude. *Amended 2026-10-27:* a maker that publishes its mark only as a raster gets an image mark instead (`ImageMark`). Gemini's own SVG fills the sparkle with an image, so the mark is the icon gemini.google.com serves, scaled to 128 px and otherwise unchanged, served from `apps/web/public/brands` and drawn on the neutral tile. The phone bundles its own copy.
- One component draws them everywhere: `ProviderLogo` (web and desktop) and its React Native twin, by provider, plan, brain or executor id. A brand-colored mark sits on a tile tinted with its color; one-color marks follow the theme; an id without a mark shows its initial; an unavailable one is only dimmed, since the makers' rules forbid recoloring a mark. `BrainLogo` is a wrapper, and `ProviderStack` overlaps several marks for a line that names more than one maker.
- A mark appears next to the name of the provider it stands for (keys, models, brains, accounts, notices), never inside our own feature names, and is never redrawn.

## Risks we accept

- **Terms.** Anthropic says personal subscriptions are for personal use and that "developers may not collect, store, or intermediate Claude.ai credentials or session tokens". OpenAI's Sign in with ChatGPT terms say: "Another user's activity must not trigger requests to the authenticated user's account." Z.ai says "Account sharing or multi-user access is prohibited" and limits the GLM Coding Plan to "officially supported tools and products"; MiniMax describes its plan as individual, interactive developer use; OpenCode Go plans "are for single-member workspaces" (all read 2026-10-23). Our server never sees a sign-in code or a plan key in the clear, and a plan answers only its owner until the owner turns on "Answers other people", whose ⓘ calls the terms a gray area, in every setup (§5). That change is audited like any other of who may talk to an agent. An owner-only autonomous agent on a Z.ai or MiniMax plan is still a gray area.
- **Several seats.** One person running several seats as several agents sits close to the usage policies' "bypassing restrictions". Accounts never switch by themselves; moving an agent to another of the owner's accounts is always the owner's own choice.
- **Logos.** Anthropic's brand terms rule out its names and logos in "your own product, feature, or company name" and say any other use "requires our written permission"; MiniMax keeps all rights to its drawing. We show marks only to say which provider something is, never redrawn and never in our feature names, and one data file means removing or swapping a mark is a one-line change.

## Consequences

- Positive: a team's seats become distinct, owned rows; any member can bring a plan to the Cloud or the server's computer; a plan never answers someone else by accident.
- Positive: four more API providers through one adapter, coding plans without our server ever holding a plan key, and logos from one source on every platform.
- Negative: more states to keep straight (a sign-in in progress, removing, signed out) and a new migration, runner protocol fields and screens.
- Negative: the providers' printed CLI output and usage endpoints can change; tests use fake CLIs, and a usage source that breaks only empties the meter, never a turn.

## Alternatives considered

- **A direct-to-computer endpoint for the code**, so it never crosses our server. Computers sit behind NAT, and on the Cloud we would issue the endpoint's TLS name ourselves, so it would be no more private than the sealed relay. Rejected.
- **Per-person routing to the workspace key**: the plan for its owner, the workspace's API key for everyone else. One agent would think with two brains and two costs depending on who is talking, and its sessions would split. The audience gate does the job. Rejected.
- **Switching accounts automatically at a limit.** Rotating subscriptions to get around limits can break the providers' terms (ADR 0041 §6). Rejected.
- **One sign-in folder for several agents' OS users** (a group, ACLs). Claude Code and Codex rewrite their credentials file readable only by the user who refreshed it, so every other agent loses it at the first refresh. Rejected.
- **Copying a login into each agent's folder.** The copies race on a rotating refresh token, and for Claude our code would handle a session token. Rejected.
- **`claude setup-token` kept by the runner and given to each turn.** It holds across users (no refresh), but our code would store a Claude.ai credential, which Anthropic's terms forbid, and such a token can't read the plan's usage. Rejected.
- **Taking turns on one folder**, lent to whichever agent runs. Agents would queue behind each other's turns, which take minutes, and the router starts up to two at once. Rejected.
- **One OS user for all of one person's agents.** It would give one sign-in to every agent of a person and drop the isolation between them (files, browser profiles, processes, ADR 0057). Not now.
- **Storing plan keys on the server**, encrypted like workspace keys. The coding plans' terms allow only their coding tools, and a server-held key could be routed anywhere. Rejected.
