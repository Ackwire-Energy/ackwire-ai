# 0009. `messages` partitioned by month

- Status: Accepted
- Date: 2026-10-14

## Decision

- `messages` is `PARTITION BY RANGE (created_at)` with monthly partitions `messages_YYYY_MM` (UTC) and a `messages_default` partition.
- drizzle-kit can't express partitioning, so migration `0000_init.sql` is hand-edited (marked in the file) and the Drizzle schema declares the matching composite primary key `(id, created_at)`; the snapshot stays in sync, so later `db:generate` runs diff correctly.
- Migration `0001_messages_partitions.sql` adds `agenteschat_ensure_message_partitions(months_ahead)` (idempotent, advisory-locked) and creates the current month plus two ahead. The server calls it on boot and daily (`ensureMessagePartitions`).
- Message ids are UUIDv7 (generated by the app), so they sort by time.
- Works on PGlite: the tests check that rows land in the right partition.

## Consequences

- No table can hold a foreign key to a message (the key would have to include `created_at`). `thread_id`, `agent_runs.trigger_message_id`, `reply_message_id` are plain uuids; integrity is enforced in code.
- A lookup by id alone scans one index per partition; fine at our scale. Thread queries use `(thread_id, created_at)`.
- Follow-ups: retention by detaching old partitions; moving rows out of `messages_default` if it ever fills (creating a partition for a range that has rows in the default partition fails); a `messages_by_id` lookup if id-only lookups become hot.
