# 0057. System mode: each agent works as its own OS user

- Status: Accepted (2026-10-24)
- Date: 2026-10-24
- Extends: ADR 0025 (connected computers), ADR 0027 (secrets to agent computers), ADR 0029 (background tasks), ADR 0030 (isolation), ADR 0056 (external provisioning)
- Code: `apps/server/runner/install-script.ts`, `service.ts`, `agent-users.ts`, `supervisor.ts`, `worker.ts`, `loopback-guard.ts`, `OP_ROUTES` in `handlers.ts`, `uploadUrl` in `push.ts`; `AGENT_WORKER_HOMES` in `packages/adapters/src/command-policy.ts`

## Context

A connected computer runs every agent's work as the OS user that runs the runner (ADR 0030, level 1). The agents on it can read each other's folders, sign-ins and browser profiles, and kill each other's processes. That is acceptable on a person's own laptop. It is not on a computer shared by agents of different people: a hosted workspace's computer, or a team's server. ADR 0030's level 3 (a dedicated user for the runner) separates the agents from the owner, not from each other.

## Decision

### 1. Install and service (Linux, root)

- `install.sh --system` installs the runner for the whole computer: the shared libraries the agents' Chrome for Testing links (`BROWSER_APT_PACKAGES`: what `ldd chrome` finds missing on a bare Debian 12 or 13 or Ubuntu 22.04 or 24.04, by apt's `t64` names where it has them; without apt, it names them), a pinned Bun checked against its SHA-256 (never a `bun` from the `PATH`, which root would then run), the bundle in `/opt/agentes-runner`, the launcher `/usr/local/bin/agentes-runner`, the home `/var/lib/agentes-runner` (0700) and the root unit `agentes-runner.service` (`KillMode=process`, so a restart leaves background tasks running). Each file and folder it writes gets its mode from the installer, never from the caller's umask (a provisioner's may be 077): the bundle 0644 and Bun 0755, in 0755 folders (the agents' users run them), the launcher 0755, the unit and the agents' slices' drop-in 0644, its folder 0755 (PID 1 warns at every read of a unit file not readable by all; one masked, a link to `/dev/null`, stays as it is), the home (0700) and its `config.json` (0600) root's alone. What apt installs keeps dpkg's modes: dpkg sets its own umask (022) for the files and the packages' scripts. Flags: `--agent-uid-range FIRST-LAST` (default 20000–29999), `--desktop`, `--no-pair`, `--no-start`, and `--enroll-file FILE` to connect with a code an external provisioner issued for this computer (ADR 0056 §10).
- The computers list says `mode: system` (from the runner's hello; `single` otherwise), so the app shows each agent working as its own user in its own folder instead of the folder the computer was connected from (root's, which no agent uses), and says allowing more takes the computer's administrator (`sudo agentes-runner folders allow …`), not the Mac app.
- `config.json` gets `mode: "system"`; pairing again keeps it. A system-mode runner never replaces itself with what the server sends: the installer updates it. `--runner-sha256 HEX` installs the bundle only when it has that hash, so whoever installs a fleet's computers can pin the runner they vouch for instead of trusting what the server serves at that moment.

### 2. One OS user per agent

- `ag-<first 8 of the agent id>`, made on the agent's first request with the lowest uid of the range that no user has and that was never handed out. `agents.json` (`[{ id, user, uid }]`) lists it before `useradd` runs, so a uid is never given twice. Users are never removed here: wiping the computer does that.
- Root runs anything as an agent through its launcher: `systemd-run --quiet --scope --collect --slice=agents-<uid>.slice -- runuser -u ag-… --` (`runuser` alone where systemd isn't PID 1), with only `HOME`, `USER`, `LOGNAME`, `SHELL`, `PATH` and `LANG`.
- Every agent's slice gets `MemoryHigh=60%`, `MemoryMax=70%`, `TasksMax=4096`, `CPUQuota=200%`, from one drop-in for the slice prefix (`agents-.slice.d`), and all agents together (`agents.slice.d`, for `agents.slice`) `MemoryMax=87%`, `TasksMax=50%` (updated 2026-10-31, see below).
- Memory is a share of the RAM, which systemd works out each time it loads the units (every boot and `daemon-reload`), so the same drop-ins fit any computer and follow one that grows. On 8 GB (7.76 GiB as the kernel counts it): above 4.7 GiB the kernel takes back an agent's cache and slows its allocations, at 5.4 GiB it stops a process of that agent, and all agents together stop at 6.8 GiB, which leaves 1 GiB to the system, the runner and the Cloud's guard. 4 GiB gives 2.4, 2.8 and 3.5 GiB (0.5 left), 16 GiB 9.6, 11.2 and 13.9 GiB (2.1 left). One busy agent can use most of an idle computer, and the others keep at least 17% of the RAM between them.
- Why: with `MemoryMax=1536M` per agent and nothing for all of them (until 2026-10-31), a headed Chrome, the desktop and a coding CLI together reached the cap while the computer had memory to spare, and Chrome's pages died (the sad tab's "error code 5": SIGTRAP, Chrome's own check when an allocation or a thread start fails). `MemoryHigh` sits close under `MemoryMax` because the kernel slows allocations more the further they go past it (up to 2 s a step) and, with no swap, slowing frees nothing: far below, a page that needs more would crawl until the agent's commands time out instead of failing and being reloaded (ADR 0040 §12). A headed Chrome with a few tabs, the desktop and a CLI with its tools pass 1,000 threads, and a thread Chrome can't start also kills its page: 4096. Half the computer's tasks for all agents keeps the system able to start a process (an administrator's login) when they run away. `CPUQuota` stays at two CPUs: under contention each slice gets its share anyway.
- A computer installed before gets them at its next runner update: the installer runs `service install --system`, which writes both drop-ins and runs `systemctl daemon-reload`, and systemd sets a running slice's limits again as it reloads. Nothing of the agents' work restarts (`KillMode=process` keeps it through the runner's restart). A running slice's `memory.peak` is a high-water mark: one that reached 1,536 MB keeps saying so until the slice starts again.
- The root runner reads `agents.slice`'s `memory.events` with each load sample (every 5 minutes), and `pong.load` carries `oomKills`: how many processes the kernel stopped for memory in the agents' slices over the day. The server keeps it with the computer's load (`machines.load`); the usage report leaves it out.
- Inside it, under systemd, the agent's Chrome runs in `agents-<uid>-browser.slice` and its AI CLIs (Claude Code, Codex `exec` and `app-server`, and the wrappers of Claude Code and Codex tasks, with whatever they run) in `agents-<uid>-cli.slice`, each start in a scope of its own (`agentes-<kind>-<uid>-<pid>.scope`). The Cloud's guard counts the agent's traffic per slice, and these names, `agents.json` and `relayed.json` (below) are all it reads. The worker spawns each one held (`scope-gate.ts`: `/bin/sh` waits on fd 3, then becomes the program) and asks root to move it (`scope.enter`). Root checks that the process's four uids are the worker's agent's and that it lies in that agent's slice, builds the slice's name from the worker's uid, asks systemd (`StartTransientUnit` with its pid, through `busctl`), and answers once `/proc` shows it there, 30 a minute per worker at most. A move that fails, or a root that doesn't answer within 5 s, leaves the process in the agent's own slice: nothing waits longer and nothing fails because of it. The prefix drop-in caps each sub-slice too, the agent's slice still caps their sum, and under contention for the agent's CPU quota each sub-slice gets a share, as the desktop's and terminal's scopes do.
- Root writes `relayed.json` in its home (`{startedAt, desktop, terminal, browserView}`, each `{up, down}`) at most once a minute when it changed: the payload bytes it relayed since it started, up toward the server, on the desktops' and terminals' data sockets and in the browser view's `browser.frame`s (down: the input people sent).

### 3. A root supervisor and one worker per agent

- The root process keeps the server's socket and runs no agent work. Each op has a route in `OP_ROUTES`: `machine` ops (the computer's accounts, folder requests and reductions) are answered by root; pause is checked there before anything else; every `agent` op goes to the worker of the request's agent. A new op doesn't compile until it has a route.
- A worker is `agentes-runner worker --agent <id>`, started through the agent's launcher on the agent's first request, or at boot when it has background tasks to watch. It refuses to run as root and serves only its own agent. It has the same managers and handlers as a single runner. The agent's folder is `<handle>-<id8>` in the agent's home, as in any workspace; the home itself keeps the agent's own dotfiles.
- The worker's own state (task journal, secrets, git credentials, browser) is in `/var/lib/agentes-runner-agents/<user>` (the agent's, 0700, in a folder root owns, 0711): outside the agent's home, so the file tools never reach it, and no agent can list another's. The agent's own code runs as the same user, so the command rules treat that folder like the runner's own home: no read of it is allowed, by our check or by Claude Code's deny rules.
- The link is the machine protocol as JSON lines on the worker's stdin and stdout, the supervisor playing the server, plus frames of its own: `worker.state` (pause, the tool switches, the limits and only this agent's allowed folders, sent after each hello and on every change), `worker.close` and the upload frames (§5). Its stderr is its log, prefixed with its user in the supervisor's.
- Sessions follow the server's. When the socket drops, each worker's session ends (its requests are aborted and its MCP calls fail or wait, as in a single runner), and the worker says hello again; it is welcomed when the server is back. Pings every 10 s keep sessions up meanwhile.

### 4. What a worker may say

A worker runs as the uid the agent's own code runs as, so the supervisor takes every frame from it as that agent's word:

- `result` and `output` only for requests it was sent (under ids the supervisor gives);
- `brain.event` and `brain.done` only for its turns in flight;
- `task.event` and `task.done` only for its own tasks: `worker-tasks.json`, in root's home, records whose each task is from its `task.start` until the server acknowledges its end;
- browser frames only for its own agent;
- `mcp.call` and `mcp.list` go up only with the run's token, which the server checks, and their answers go back to that worker only. A call without a token is refused here: for those, the server takes the task id as proof of whose call it is, and other agents' task ids aren't secret on a shared computer;
- never the computer's own frames (`runner.state`, `access.*`, `accounts.changed`).

A worker that sends a line longer than a frame, or leaves 64 MB of what it was sent unread, is stopped.

### 5. Uploads without the machine token

No worker holds the machine token. For `push`, the worker reads or zips the file with its own path checks and sends the bytes to the supervisor in 1 MB pieces. The supervisor uploads them once per `push` request, with the token, to that request's URL path on the server the computer is paired with (`uploadUrl` in `push.ts`): the server builds the URL from its public address, which its own computer may not reach, and the token goes to no other host. Only the file's name, type and hash come from the worker; more bytes than the request allows are refused.

### 6. hello, restarts

- `hello.tasks` lists every task in `worker-tasks.json` as `running`, whether its worker runs or not: the server keeps them, and each worker sends `task.done` again until it is acknowledged.
- A worker that stops fails what it was running. It starts again after a backoff (1 s, doubling to 60 s while it keeps stopping soon after starting): at once when it has tasks to watch, else on its agent's next request. One that doesn't say hello within 20 s is stopped.
- When the supervisor restarts, its workers see their stdin close and exit; background tasks keep running (ADR 0029) and the next workers pick them up from their journals.

## Consequences

- Agents of different people can share one computer: files, sign-ins, browser profiles and processes belong to each agent's uid. An agent's code can rewrite its own worker's state but never get another agent's work accepted.
- A worker costs tens of MB, and only agents that work have one.
- The limits in `config.json` (tasks, brains) apply to each agent.
- Accounts (ADR 0041) stay in root's home: in a worker, a turn that names an account fails with `account_missing` until that account's folder belongs to the agent's user.
- Chrome's debugging port and the browser stream have no authentication of their own. In system mode each agent has a fixed pair in TCP ports 10000–29999. The root supervisor installs an nftables owner rule for every configured agent uid before workers start, and a systemd cgroup bind policy prevents another agent from taking that pair. The policy also denies TCP `bind(0)`: the pinned browser stream otherwise falls back to a random port when its assigned port is occupied. An actual IPv4 and IPv6 bind probe must pass before an agent process starts. The root runner requires systemd, `nft`, `ss`, and a nonoverlapping Linux ephemeral port range; it refuses to start an agent process if the bind policy is ineffective. Explicit TCP binds outside the reserved range still work; agent TCP `listen(0)` does not.
- Other agent-owned loopback listeners are discovered from `ss` every 2 s and guarded by the same nftables table. A newly opened listener is reachable before the next scan, and a stale owner exception can survive until that scan after a port is reused. These arbitrary local ports are not yet a hard boundary between agents of different people. An `ss` failure keeps the last applied rules.
